## 0. 三条铁律

1. **先读后动**：每次任务开始，必须按 §1.2 固定顺序**全量阅读** 7 个核心文件——不可选项，不可跳过。
2. **写必有因**：任何文件写入必须命中 §3.2 对应的「写入触发条件」；命中不了就不写，禁止为写而写。
3. **交付必同步**：P4 记忆库同步检查（§5）与 P5 Git 推送（§6）全部通过后，才允许 attempt_completion。

## 1. 任务生命周期与文件读写时机（核心）

### 1.1 六阶段定义

| 阶段 | 名称 | 关键动作 |
|------|------|---------|
| P0 | 任务启动 | 记忆重置后全量必读记忆库 |
| P1 | 理解与规划 | 澄清需求 → 生成/修订规划文档并定稿 |
| P2 | 实施开发 | 编码前查防回归清单 → 实施 → 错误实时入档 |
| P3 | 验证与调试 | 测试、排错、复用/更新错误条目 |
| P4 | 交付同步 | 逐文件同步检查 → 更新受影响文件 → 输出检查清单 |
| P5 | Git 收尾 | add → commit → push → attempt_completion |

### 1.2 P0：任务启动全量必读（固定顺序，不可调换）

| 顺序 | 文件 | 读取目的 |
|---|---|---|
| 1 | projectbrief.md | 项目是什么、范围边界在哪 |
| 2 | productContext.md | 为什么做、为谁做、应如何工作 |
| 3 | activeContext.md | 当前重点、最近变更、下一步 |
| 4 | systemPatterns.md | 架构与技术决策、已知陷阱与规避模式 |
| 5 | techContext.md | 技术栈、环境、依赖与工具约束 |
| 6 | progress.md | 已实现/待构建，避免重复劳动 |
| 7 | errorlog.md | **防回归清单（编码前必查）**、未解决错误现状 |

### 1.3 核心文件读写时机矩阵

图例：R=读，W=写，–=不涉及；**粗体**=强制动作；W*=仅当满足 §3.2 写入触发条件时才允许写。

| 文件 | P0 启动 | P1 规划 | P2 实施 | P3 调试 | P4 交付同步 | P5 Git |
|------|---------|---------|---------|---------|-------------|--------|
| projectbrief.md | **R** | R | – | – | R；W* | – |
| productContext.md | **R** | R；W* | – | – | R；W* | – |
| activeContext.md | **R** | **W** | R；W* | R | **W** | – |
| systemPatterns.md | **R** | R | **R**；W* | R；W* | R；W* | – |
| techContext.md | **R** | R | R；W* | R；W* | R；W* | – |
| progress.md | **R** | R | – | – | **W** | – |
| errorlog.md | **R** | – | **W** | **R+W** | **R+W** | – |

强制动作说明：

- **P0 全列 R**：记忆重置后必须全量读，无豁免；
- **activeContext.md P1 写**：规划定稿时写入「工作重点 + 计划 + 下一步」；
- **systemPatterns.md P2 读**：编码前必读「已知陷阱与规避模式」小节；
- **errorlog.md P2 写**：唯一允许且要求实时写入的文件；
- **activeContext.md / progress.md P4 写**：交付收口必写；
- **errorlog.md P4 读+写**：状态收口（🔴→🟡→🟢 流转、复现更新原条目）。

### 1.4 各文件「何时才能写」速查

| 文件 | 主要写入时机 | 备注 |
|------|-------------|------|
| errorlog.md | P2/P3 中满足记录原则**当场写** | 唯一实时写文件，禁止攒到 P4 一次性补记 |
| activeContext.md | P1 规划定稿写「计划」；P4 交付前写「结果」 | P2 仅当工作重点漂移时小步更新 |
| progress.md | 仅 P4，且功能**已验证落地**后 | 半成品/未验证状态禁止入档 |
| projectbrief.md | 仅 P4，且范围/目标/阶段描述真实变化 | 全库写入频率最低的文件 |
| systemPatterns.md | P3/P4：errorlog 沉淀出口的普适教训；架构变化 | 只写可复用模式，不写流水账 |
| techContext.md | 新依赖、工具链/构建/环境约束变化时 | 环境坑先入 errorlog，约束结论入此 |
| productContext.md | 需求语义变化且经用户确认后（P1 或 P4） | 不因实现方案调整而写 |

### 1.5 附加文件时机

| 类型 | 创建/写入时机 | 读取时机 |
|------|--------------|---------|
| 复杂功能规划文档 | P1 创建并定稿 | P2/P3 只读参照；实施偏差过大时回到 P1 修订 |
| 集成规范 / API 文档 | P1~P2 按需 | P2/P3 按需 |
| 测试策略 / 部署流程 | P1~P3 按需 | 对应验证/发布环节 |

## 2. 记忆库结构

### 2.1 核心文件（必需，全部为 Markdown）

1. **projectbrief.md** —— 项目「事实来源」
   - 塑造所有其他文件的基础文档；不存在则在项目开始时创建
   - 定义核心需求、目标与范围边界
2. **productContext.md** —— 项目「为什么」
   - 解决什么问题、应如何工作、用户体验目标
3. **activeContext.md** —— 项目「现在」
   - 当前工作重点、最近变更、接下来的步骤、当前决策与考量、重要模式与偏好、经验教训
   - 「当前处理中的错误」小节：**仅列错误编号与状态**，详情一律指向 errorlog.md
4. **systemPatterns.md** —— 项目「怎么建」
   - 系统架构、关键技术决策、设计模式、组件关系、关键实现路径
   - 「已知陷阱与规避模式」小节：承接 errorlog.md 沉淀的普适教训
5. **techContext.md** —— 项目「用什么建」
   - 技术栈、开发环境设置、技术约束、依赖项、工具使用模式、环境类约束结论
6. **progress.md** —— 项目「到哪了」
   - 已实现功能、待构建内容、当前状态、已知问题**摘要 + 链接**、项目决策的演变
7. **errorlog.md** —— 项目「坑在哪」（问题—解决方式的唯一事实来源）
   - 错误分类：构建 / 依赖 / 运行时 / 逻辑 / API 误用 / 环境工具链
   - 错误编号：`ERR-<三位递增序号>`（如 ERR-014），全库唯一引用键
   - 标准条目字段：编号、错误现象、发生上下文、发生时间（YYYY-MM-DD HH:MM）、根本原因、解决方式、解决时间（YYYY-MM-DD HH:MM）、验证结果、教训、状态
   - 生命周期：🔴 未解决 → 🟡 规避中 → 🟢 已解决；复现时更新原条目，禁止另开新条目
   - 防回归清单：高频错误与易踩陷阱的规避要点，**编码前必查**
   - 沉淀出口：普适教训 → systemPatterns.md；环境约束 → techContext.md；避免本文件无限膨胀

### 2.2 附加上下文

当有助于整理时，在 `memory-bank/` 目录内创建额外文件/文件夹：复杂功能文档、集成规范、API 文档、测试策略、部署流程（读写时机见 §1.5）。

## 3. 写入触发条件与禁写边界（防膨胀核心）

### 3.1 记录原则（errorlog.md 专用）

- **必须记录**：导致任务中断或返工的错误；多次尝试才解决的问题；环境与依赖相关的坑；AI 生成代码的典型错误模式
- **不予记录**：当场修复且无副作用的一次性笔误；与项目无关的临时试验错误

### 3.2 各文件写入触发 / 禁写清单

| 文件 | 允许写入（触发条件） | 禁止写入 |
|------|---------------------|---------|
| projectbrief.md | 范围、目标、阶段描述变化 | 实现细节、技术方案、错误信息 |
| productContext.md | 需求语义变化且经用户确认 | 架构与代码级细节 |
| activeContext.md | 重点/计划/下一步/决策变化；错误仅引用编号 | 错误详情、历史流水账 |
| systemPatterns.md | 新模式、新架构决策、普适教训沉淀 | 一次性技巧、项目外通用知识 |
| techContext.md | 依赖、工具链、环境约束变化 | 业务逻辑 |
| progress.md | 功能状态**经验证后**变化 | 问题描述详情、未验证状态 |
| errorlog.md | 命中 §3.1「必须记录」 | 命中「不予记录」的琐碎错误 |

## 4. 文档更新触发（P4 强制同步之外的更新时机）

1. 发现新的项目模式时（→ systemPatterns.md）
2. 实施重大变更后（→ 按 §5.2 映射表更新）
3. 用户请求 **更新记忆库** 时（等效执行 P0 全量重读 + P4 全量检查，必须审查所有文件）
4. 当上下文需要澄清时
5. 每次任务交付前——P4/P5 强制执行，无需用户提示

## 5. 📌 任务后同步检查（P4，强制，交付前自动执行）

### 5.1 检查流程

1. **确定影响范围**：`git status` / `git diff` 查看本次实际改动文件清单，作为影响范围判断的客观依据（不凭记忆）
2. **逐文件检查**：对 `memory-bank/` 下**全部** md 文件逐一回答「本次变更是否影响该文件内容」：
   - 受影响 → 立即更新（交叉引用保持一致；错误详情统一指向 errorlog.md 的 ERR 编号）
   - 不受影响 → 显式记录「无需更新 + 原因」，**不允许静默跳过**
3. **输出检查清单**：在交付说明（attempt_completion）中逐文件列出：
   - `✅ 已更新：<文件名>（<更新内容摘要>）`
   - `➖ 无需更新：<文件名>（<原因>）`
4. **一致性红线**：多个文件对同一事实的描述必须一致（版本号、构建状态、决策结论、错误编号）；发现矛盾时以**最新实际代码状态**为准修正
5. **禁止带病交付**：发现遗漏（某文件应更新但未更新）必须先补齐再交付

### 5.2 变更 → 受影响文件映射表

| 变更类型 | 必查文件（按顺序） |
|---------|------------------|
| 新增/解决错误 | errorlog.md（首要）→ systemPatterns.md（普适教训）→ techContext.md（环境约束） |
| 功能迭代/版本推进 | activeContext.md → progress.md → projectbrief.md（阶段描述） |
| 架构/分层变化 | systemPatterns.md → projectbrief.md |
| 新依赖/工具链变化 | techContext.md |
| 交互模式变化 | activeContext.md → techContext.md |

### 5.3 辅助手段

- 首轮全量检查使用 §7 清单模板（7 个核心文件逐一过）
- errorlog.md 新条目必须含时间字段（YYYY-MM-DD HH:MM）；历史条目未带的，触碰时补齐

## 6. 🔄 Git 同步（P5，强制，同步检查通过后执行）

### ⭐ 强制规则：执行完成即同步 GitHub

- 每次任务执行完成且产生任何文件修改（代码 / 记忆库 / 配置 / 构建产物），必须同步到 GitHub 远程仓库（`git add -A` → `git commit` → `git push`）——交付的强制收尾步骤，**不依赖用户提示**
- 交付前确认：`git status` 干净（无未提交变更）；`git status -sb` 本地分支与远程一致（无 ahead/behind）
- push 成功后在 attempt_completion 附**提交哈希与远程分支**（如 `3fc7a86 → origin/master`）
- ❌ 禁止只 commit 不 push；禁止把「同步远程」留给下一次任务

### 提交规范

- 消息格式：`<类型>: <摘要>`（如 `feat: 配方页删除行/列+确认弹框(v1.4)`、`fix: CellFocused单击不触发改双订阅`、`docs: 记忆库同步`、`refactor:`、`build:`）
- 一次性提交本次全部变更（代码 + 记忆库），保持提交原子性

### 失败处理

- **push 失败**（网络/SSH 密钥/远程权限）：**不回滚本地 commit**，在交付说明中记录失败原因，下次任务开始时优先补推
- 仓库无远程或首次使用：仅执行到 commit，并提示用户配置远程

## 8. 标准收尾流程（P0 → P5 全链路）

```text
任务开始
  → P0 按 §1.2 顺序全量必读
  → P1 澄清需求 → 规划文档定稿 → 写 activeContext.md（重点 + 计划）
  → P2 编码前查 errorlog.md 防回归清单 → 实施 → 错误实时入档
  → P3 验证调试 → 更新 errorlog.md 状态
  → P4 ① git status/diff 确认改动范围 → ② 按映射表逐文件检查
       → ③ 更新受影响文件 → ④ 在交付说明输出检查清单
  → P5 git add -A ; git commit ; git push（PowerShell 终端用 ; 分隔）
       → 核对 status 干净、无 ahead/behind
  → attempt_completion（附检查清单 + 提交哈希与远程分支）
```
